## 三、24 条请求的端到端链路（`eval/result_stdlib.csv`）

| 项目 | 实测值 |
|---|---|
| 请求数 | 24（人工标注 easy 13 / hard 11） |
| 路由结果 | easy 14 / hard 10 |
| 路由准确率 | **95.8%（23/24）** |
| 决策来源 | 规则层 **17 条（70.8%）**、模型层 7 条（29.2%）、兜底 0 |
| 平均延迟 | 3105 ms（最长 12.1 s：长文生成 768 token 上限） |
| 实际成本 | **¥0.0149** / 24 条（本地折算单价） |
| 同 token 云端牌价基线 | **¥0.0514** / 24 条（入 ¥0.005、出 ¥0.015 per 1k） |
| 成本占基线比 | **29.0%** |
| token | 输入 2854 / 输出 2475 |
| 失败 / 报错 | 0 |

### 唯一的判错案例（可写进报告当分析素材）

| 查询 | 标注 | 判定 | 决策层 | 原因 |
|---|---|---|---|---|
| 帮我 review 这段 SQL：`select * from orders wh…` | hard | **easy** | 模型层 | 模型认为"简短且直接" |

**诊断**：规则层的关键词表里没有任何 SQL 特征（`select`/`join`/索引/慢查询），"review" 也不在强特征里，于是落到模型层；模型按"文本很短"判成了 easy。**修复方向明确**：规则层补 SQL/代码粘贴检测。这不是"模型不行"，是"规则层覆盖不足"——正好是 P1 的第一项任务。

## 四、必须如实说明的局限：云端支路未连通

本轮 `CLOUD_API_KEY` 填入后，**24 次云端调用全部失败**（脚本自动降级到本地，故 `result_stdlib.csv` 里 24 行的 `model` 全部是本地模型路径，没有一行是 `deepseek-chat`）。

后果（写报告时必须这样表述，不能回避）：

1. **不能说"混合路由比全云端省 71%"。** 29.0% 这个数只说明：在相同 token 量下，本地推理的成本是云端牌价的 29%——这是**价差**，不是**路由收益**。
2. 本轮"混合路由"实际等价于"全本地"，路由的成本收益**尚未验证**。
3. 表里"全云端"行的 ¥0.0162 **不是云端成本**，而是云端失败后降级到本地的成本（且因强制走 hard 分支、生成更长，反而略高于全本地 ¥0.0147）。这本身是一个有意义的工程观察：**降级路径必须记账，否则成本会算错。**

### 待补（P1 首件事）

```bash
python tools/preflight_stdlib.py                  # 云端 API 是否 [OK]
curl -s https://api.deepseek.com/v1/models -H "Authorization: Bearer $KEY" | head -3
```

失败三种可能，按概率排序：Key 未生效（`sed` 未匹配/多空格）、账户无余额、集群出网策略拦截该域名。逐个排掉即可。

## 五、可以直接写进报告的结论段

> 本工作在 AUP Learning Cloud 的 AMD GPU（Radeon 8060S，ROCm 7.13）上完成了 P0 概念验证：模型以 fp16 加载，峰值显存 2.99 GB，单请求平均吞吐 32.6 tok/s、平均延迟 2705 ms；24 条标注请求的端到端链路零失败，路由准确率 95.8%，其中 70.8% 的请求由零成本的规则层直接判定，计费链路可逐请求归因到 token 与金额。
>
> 由于平台镜像未提供 vLLM 且 gfx1151 缺少成熟推理框架支持，本工作改用 transformers 自建 OpenAI 兼容服务完成预演；云端 API 支路在本轮未连通，故三策略的成本对比尚不完整，该部分与并发压测一并列为 P1 任务。已测得的本地推理成本为云端牌价的 29%，该比值反映软硬件选型的价差，不等同于路由策略的收益。
